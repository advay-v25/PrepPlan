# PrepPlan entry experience · 23 November 2026

## Scope and verdict

Public sign-in, signup, reset request, email resend, link failure and the anonymous setup redirect were captured on PrepPlan at 1280 × 900 and 390 × 844. The account-only screens were rendered from the current components in a separate local copy with synthetic setup state, a fixture plan, and a simulated reset-request acknowledgement. The success-banner view was opened directly using its URL. These are visual and interaction checks. Delivery, provider callback, password writes, onboarding saves and actual draft acceptance need a connected disposable project for end-to-end proof.

The visual system is consistent, forms are recognisable and all sampled screens stayed within their viewport width. The largest usability problems are recovery actions that fail to identify the next step, settings for class-led and mature entries that are too easy to miss, and mobile setup that hides important details below a sticky action. Keep the brand, clear labels, explicit setup acceptance and optional detail. Simplify the task a student has to do on each screen.

## Authentication and recovery

| Screen | What works | Critical finding and required improvement |
|---|---|---|
| Sign in | Google and email are distinct. The password visibility button toggled on live. Protected entry kept the requested Calendar/onboarding destination. | The rendered password field's accessible name includes “Forgot password?” and “Show password”. Give the input a dedicated label, the toggle its own name, and recovery a sibling link. Give the security check a clear status next to the primary action and preserve fields if its retry needs to reload. The example’s “Rebuilt every Sunday” message applies to self-study only. |
| Signup | Clear brand, full name and email labels, visible password guidance. | On mobile the full form, duplicated policy links and security widget fill most of the first view. The example week then adds another long section. Keep policy access for each entry method while reducing repeated presentation, and collapse the optional example. Replace “About a minute” with an accurate next step that allows for verification and setup. |
| Email resend / check email | Neutral disclosure avoids revealing account state. Recovery actions are available without an active study workspace. | “Verify your email” is the heading on a form for requesting another message. Name it “Send a new confirmation email”. After submit make it clear whether the message was requested versus delivered, with the current address visibly editable and a resend timer or feedback when applicable. |
| Confirmation link | Explicit continue is appropriate for links that a mail scanner may visit. It is separate from a valid signed-in session. | “Continue” gives little context. Use “Confirm email” or “Continue to new password” and keep the matching resend as the recovery action. A bare /auth/verify should explain which action to take, without claiming an email check succeeded. |
| Reset request and inbox acknowledgement | Simple email-only form and privacy-safe wording. The local form showed “Check your inbox” after a simulated acknowledgement. | The acknowledgement’s main action is “Back to sign in”, which is secondary to finding the reset link. Make “Check your email and follow the link” the clear status. Keep edit or retry address and sign-in as secondary. Preserve neutral account-disclosure wording. |
| Confirm reset and new password | The recovery intent is distinct from standard sign-in. New and confirmation inputs are visible. | Confirmation contains “Already confirmed? Choose your password” as well as Continue. Keep one obvious initial route, then let a verified recovery session resume the new-password screen. Make requirements and matching feedback perceivable before submit, with a focused error and an explicit state for expired or unconfirmed save outcome. |
| Expired, used, cancelled and success states | There is a dedicated error screen and a sign-in banner. | The live expired-link variant tells the user to complete **Google** sign-in in the same browser, even though this is a generic expired-link view. The main action is “Try signing in”. Return a safe, enumerated recovery flow type from the server and offer “Send a new reset link”, “Resend confirmation” or “Try Google again” accordingly. Mark a successful reset only from a trusted receipt/session state. The current sign-in banner can be rendered simply by opening its success URL. |
| Add a password after Google | The screen explains what adding a password enables. | There is only “Save and continue”, which adds a second credential decision to Google onboarding. Review whether email/password fallback is optional for this product. If optional, offer “Continue with Google only” and a settings entry for adding a password later, backed by an explicit server auth-state contract. |
| Setup entry and gate | An anonymous direct URL routes through sign-in. Source enforces step order. | Tell a verified student where they will resume, preserve intended destination, and test expired sessions mid-form. Provider integration, real recovery and independent browser sign-up still need proof. |

## Onboarding

| Step | What works | Critical finding and required improvement |
|---|---|---|
| 1 · Exam | Month-first and booking details support a tentative target. | Start with “Which exam month are you aiming for?” Use the four month choices available for the supported year. Show the exact date only after a booked response. Say precisely how a provisional month is used and where to add the date later. Keep timezone automatic with a visible correction in scheduling if needed. |
| 2 · Study style | Plain route cards. Selecting Live classes revealed class timing choices. | Two self-paced and two class-led options carry different scheduling semantics but the distinction takes reading. Show the consequence directly under the chosen card. Ask for the next class only when relevant, and phrase the provisional schedule as a temporary plan if it is unknown. |
| 3 · Starting point | Four simple stages, possible reading refinement, and a mock option. | “First pass complete” seeded a visible “10 of 10 topics covered once” in the sample. Keep it clearly self-reported. The same choice hides whether the student has already revised and how the latest mock went. Offer a lightweight follow-up for mature entrants, with no-score and “I’ll log it later” paths. Surface only one next useful field group. |
| 4 · Your week | Presets and choices for a changing schedule or a week with no study. The Saturday preset and 45-minute choice both responded. | The sample expanded to 1,881 CSS px at 390px after two choices. Each day has a generic “Add”, and “Weekends” means Saturday for the self-study preset. Use “Saturday morning” and one clear day/window editor, with specific accessible names. Put max sitting close to availability and show protected commitments when relevant. Explain a flexible allocation means a day and duration. |
| 5 · Review | Saved answers, an editable summary, assessment state and explicit acceptance. | On phone the sticky accept area sits over the first week’s heading on first view, and the summary precedes the plan. Preview should lead with a short schedule summary, what fits, what waits and why. Reserve space for the sticky controls and let scroll and keyboard reveal focused content fully. The fixture shows the “Nothing is placed yet” checkpoint copy alongside a study sitting. Distinguish nothing planned from “finish and confirm some work to see what can be tested”. Explain why the first week is a baseline in plain language. |
| All five progress states | Current step is clear visually and marked with aria-current. | At 390px four progress links had no accessible name because CSS hides the inactive text. Give each step a name regardless of viewport, describe completed and unavailable states in text, and keep future steps non-interactive until reachable. Preserve Back and Reload behaviour. Avoid the live plan mini-calendar on any phone screen where it competes with the decision. |

## Priority and verification

1. Fix labels, mobile focus and safe-area obstruction, auth errors and recovery actions. Add keyboard and screen reader assertions. Exercise no-link, expired, reused and unknown-result paths with synthetic tests. Verify real mail, Google and a recovery session on the disposable project before release.
2. Simplify setup inputs and narrow the backend reads in the [revamp plan](PREPPLAN-END-TO-END-REVAMP.md). Drive fresh self-study, a class-led schedule with two occurrences and a mature February candidate with a poor mock. Include slow loading, a stale save, resume after refresh, a valid empty week and accepting only once.
3. Check stage and phone layout on short and tall viewports, keyboard open, reduced motion and text zoom. Confirm errors are associated with the correct input, focus stays visible, and a valid answer is never lost when navigating.
