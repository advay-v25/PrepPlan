# PrepPlan security and authentication hardening

## Verified findings and changes

| Priority | Finding | Change or release action |
|---|---|---|
| First | A credential-like database URL remains in Git history. The current source excludes the file. Its validity and rotation status are unknown. | Rotate the affected database password, update server and migration connections, verify the new connection, and invalidate the old credential. Review access logs and repository secret scanning. Treat history cleanup as a separate coordinated operation after rotation. |
| First | The live sign-in page rendered and its anti-bot check eventually enabled the submit button. A slow, failed or unavailable check could silently block email authentication. | The form now reports the check's state and offers a retry. The auth request has a deadline. Turnstile and server rate limits remain enforced. |
| First | Signup and profile writes allowed arbitrary text as a name. Profile creation also copied provider metadata unchecked. | Signup and Settings enforce one Unicode name rule. The migration enforces it on database writes and uses `Student` when imported metadata is absent or invalid. Existing names remain readable and other profile updates continue to work. |
| Next | Signed-out auth pages initialized the auth client before rendering. Public-key precedence also differed across clients. | Cookie-free requests skip the auth client. Existing-session checks are bounded. The server and email paths prefer the publishable key. Authentication timing logs contain action and duration. |
| Next | Authentication exception and provider errors reached operational logs as raw text. | Authentication errors and rate-limit errors record categories only. Profile write failures report an unconfirmed save and retain the edit. |
| Next | No repeatable client-bundle credential check existed. | `npm run audit:client-secrets` checks public env aliases and built browser assets. It reports variable names and paths. It is a release check and covers configured values and recognized privileged-key patterns. |

Name inputs accept letters with attached Unicode marks and up to 100 characters after normalization. A single space, ASCII hyphen, straight apostrophe or right curly apostrophe can separate letter groups. Runs of ordinary spaces collapse to one. Leading, trailing, repeated or mixed punctuation is refused, as are digits, emoji, markup, controls, invisible formatting and lookalike punctuation. The database migration leaves existing names in place until edited.

## Release sequence

1. **Secure credentials.** Identify the database credential in repository history without copying its value. Rotate it at the affected project. Check GitHub secret scanning, Vercel logs and prior deployment environments. Keep Supabase server keys, DB passwords, mail and AI keys, the cron secret and the recovery signing secret server-side. The browser may receive the Supabase publishable key, the Turnstile site key and the site URL. Keep production and testing projects separate. Use an independent `APP_SECURITY_SECRET` and plan for outstanding recovery links to expire when rotating it. [Supabase API keys](https://supabase.com/docs/guides/api/api-keys)
2. **Rehearse the schema and release.** Apply the profile migration to an isolated copy of the production schema and check the auth trigger, existing rows, the owner-only update command, fresh deployments and backup restore. Apply the migration to the approved production target through the migration ledger. Build with the production settings and run the browser-asset check before publishing. A rollback to the previous app build can retain the additive database guard.
3. **Validate production providers.** Confirm the canonical `https://www.prepplan.si` origin and apex redirect, exact Google callback, both necessary Turnstile hostnames, verified email sender, and Supabase verification and reset templates. Review provider-side password rules, rate limits and session settings for direct Auth API use. Test from a normal browser and a restrictive connection. Use the existing [authentication setup guide](AUTHENTICATION-SETUP.md).
4. **Run the account matrix.** Test invited and uninvited accounts, email confirmation, tested and expired links, Google cancellation and return, password reset, session refresh, device and global sign-out, reauthentication, account export and deletion. Check old sessions, concurrent retries, cross-account requests and ordinary versus reviewer access in the test project. Exercise provider outages without weakening admission or anti-bot protections. Require evidence on desktop and mobile and repeat a safe signed-in smoke test after production deployment.
5. **Measure the full experience.** Measure auth page response, challenge time, submission, provider callback, and time to the next usable screen separately. Record at least 30 sequential samples per journey before measuring p95. Measure Home, Calendar, Curriculum and Tests with normal and long histories. Consolidate independent reads and request-local duplicate queries without sharing private data across users. Keep the current verified session and authorization gates. [Supabase SSR authentication guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs&router=app)
6. **Operate it.** Alert on sustained auth 503s, unexpected 429s, callback errors, and broken mail/cron. Review role grants and RLS with two disposable users. Establish owner MFA, backups, restore drills, quarterly credential review and an incident runbook for key rotation, session revocation, and release rollback. Re-run redacted secret checks and dependency audits on each release.

## Production handoff

- **Rotate both historical credentials.** The database credential was confirmed in commit `a24bee8`. The reminder workflow contained a literal cron credential in commit `6ef7508`. The current workflow reads `secrets.CRON_SECRET`. Rotate the host and GitHub Actions cron values together and verify one scheduled worker run. Removing a value from source or environment configuration leaves the old credential valid until it is rotated or revoked.
- **Preview the migration against the exact project.** Use a private `.env.production.local` with `NEXT_PUBLIC_SUPABASE_URL`, `MIGRATION_EXPECTED_PROJECT_REF`, and the rotated `SUPABASE_DB_PASSWORD`. On an IPv4-only connection, copy the Session pooler host and `postgres.<project-ref>` user from Supabase **Connect** into `SUPABASE_DB_HOST` and `SUPABASE_DB_USER`. Set `SUPABASE_DB_PORT=5432` for that connection. Run `npm run migrate -- --env=production --dry-run` and verify the target and pending files before scheduling the apply. [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres)
- **Confirm replacement keys before removing legacy variables.** Give the host a dedicated 64-character random hex `APP_SECURITY_SECRET`. Confirm the running app and worker use the replacement Supabase server key and publishable key before removing legacy variables. Run the bundle audit against the actual build directory if it differs from `.next/static`.

## Verification boundaries

The production build, `npm run verify`, 15 application name cases, 24 isolated database security checks, and local production auth smoke checks passed. The smoke checks covered public entry, protected return links, and a refused invalid name. The secret audit checked 55 local build assets and 14 JavaScript assets served by the live landing, sign-in, signup and reset-request pages. It found zero matches within that scope. A synthetic marker test verified that findings omit the credential value. The production dependency audit reported zero advisories at the time of the run.

The Turnstile retry browser regression passed on desktop and at 390 pixels using a local build with a simulated widget. It covers the sign-in timer, the provider timeout callback on signup, failed script loading, and retry preserving the typed email. No auth submissions are made in this test.

The live public screens were checked without submitting credentials. Production credential validity, mail delivery, Google return, and signed-in live timing require provider-side verification. Development credentials in the current staging environment are insufficient to create disposable users for the full account browser journey. The isolated name migration test does not substitute for rehearsal on the full deployed schema. No production keys, dashboard controls or database rows were changed.
